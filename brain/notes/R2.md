## Decisions
- **Rate only settled contests, in strict order.** A daily accepts legacy-alias submissions for a day after closing (`isSettled`), so the rater waits, and stops at the first unsettled contest so a season (no grace) is never rated ahead of an earlier daily. Order: `closes_at`, daily before season, id.
- **Lock**: `arena_meta` row `rating_lock`, claimed with a conditional upsert (2 min TTL). Loser does nothing. Each contest is also one transaction that first checks `rating_contests` is empty for it, so a stale-lock overlap cannot double-rate. Max 4 contests per run; the backlog drains on later requests.
- **Budget guard**: rating pauses at `tight`/`readonly` (before play pauses at `readonly`), catches up later by itself. Extra env knobs (not in the plan): `TENDRIL_RATING=off`, `TENDRIL_RATING_FROM=YYYY-MM-DD` (launch gate; useful for the 23-30 Nov shadow week and for starting rated play on 1 Dec). Say if unwanted.
- **Eligibility** as briefed; "reached par" = the entry used has `par_tick`. Account age is measured at the contest's close (deterministic for recompute). Dev logins, the model runner and accounts not signed in since 008 have no `github_created_at` and are unrated.
- **Duplicates**: log-hash check reuses the board's grouping (first submitter keeps the place, later identical logs out). Added normalised-source check (`normalizeSource`: strips comments/spacing/indent width, keeps nesting). It does NOT rename-normalise identifiers; renamed copies with the same log are still caught by the log hash. Program text is pruned after 2 days, so the verdict is stored in `rating_contests.summary.dupSource` and reused by recompute.
- **Ties**: players with an equal board value and net worth share a place (engine averages). Different from the board, which breaks ties by time.
- **Per discipline best entry**: Overall = best net worth among par-reaching human entries; Speed = lowest `par_tick`; Brevity = fewest tokens (needs tokens and par).
- **Storage**: besides the contract columns, `rating_profiles` has nine mirror columns (rating, events, last closes_at per discipline) with partial indexes, so ladder, rank and percentile are index reads rather than JSON scans. Still one row per player, one write per participant. History capped at 400 rows per discipline.
- **`/ratings/me/latest`** writes nothing: the client passes `seen=<challengeId>` (and keeps it in local storage). If R4 wants server-side "seen" state, that needs a column.
- **Field-size padding (R1 caveat)**: the server gives the engine only players meeting every eligibility rule (par, human, 14-day GitHub, not a duplicate), and the engine drops placement accounts once 30 established exist. `field_size` stored = the engine's field. Test: 52 young-account fakes beside 8 real players leave field 8 and the real players' deltas equal the no-fakes run. Remaining hole: fakes with 14+ day GitHub accounts that reach par still count; R9 (and the engine's median-band idea in R1.md) should decide.

## Writes per contest
- 1 profile row per participant (even if rated in all three disciplines) + 3 `rating_contests` rows + 1 resume marker = **N + 4**; each lazy run adds 2 (lock claim and release). Tested: 40 participants = 44 writes, and a second contest rewrites the same 40 rows = 44.
- A skipped contest (field < 8) costs 4 writes. Profile rows go in multi-row upserts of 40, so a 1,000-player contest is about 25 statements. Reads: one pass over the contest's entries, one over their sources, profile loads in chunks of 400; board decoration reads <= 101 profiles per board request.
- Example: 300 rated players a day plus a weekly season is about 300 x 35 = 10.5k rows a month, far under the 8M budget.

## Caveats / for others
- Accounts that signed in before 008 have no account date and stay unrated until they sign in again (sign-in refreshes it).
- Deleting a user cascades away their entries and ratings; a recompute afterwards would differ from history. Accepted.
- Recompute is not interactive-safe against a crash: it saves the old `rated_at`/`dupSource` in `arena_meta.rating_recompute` first and a rerun resumes from that.
- `ratingModels()` returns `{models: []}` for R7. Image routes not built (R5).
- R3/R4/R6: `rating` per discipline is null when never rated; `tier.next` is the next floor or null.
